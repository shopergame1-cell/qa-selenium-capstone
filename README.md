# QA Selenium Capstone

Capstone-проєкт курсу QA Mentorship: фреймворк на **Page Object** + **5 тестів**, які мусять
стати зеленими. Приймання — **зелений прогін GitHub Actions** у твоєму форку (не слова, не скріншот).

## Як працювати

```bash
# 1. Форкни репозиторій і клонуй свій форк
git clone https://github.com/<твій-логін>/qa-selenium-capstone.git
cd qa-selenium-capstone

# 2. Подивись, що саме вимагається (методи з TODO)
grep -rn "TODO" src/test/java | head -20

# 3. Реалізуй Page Object-и, поки тести не стануть зеленими
#    (локально: mvn test, якщо в тебе є JDK 17 і Chrome)

# 4. Запуш і відкрий Actions — коли прогін зелений, прикріп його посилання в курсі
git push origin main
```

## Що перевіряє CI

`mvn -B -q test` на Ubuntu з Java 17 і Chrome у headless-режимі: 5 тестів проти публічного
стенду Swag Labs (`https://www.saucedemo.com/`, відкритий демо-застосунок Sauce Labs).

## Практики стенда (вправи, які навмисно падають)

Крім тестів capstone у репозиторії є чотири навчальні вправи — вони лежать у
`src/test/java/capstone/stand/` і вмикаються профілем `stand`:

```bash
# послідовний прогін — зелений (вправи себе пропускають)
mvn -B test -Pstand -Dparallel=none -Dparallel.enabled=false

# паралельний прогін — ЧЕРВОНИЙ, і це очікуваний результат вправи
mvn -B test -Pstand -Dparallel=methods -Dparallel.enabled=true

# падіння з різних причин — теж ЧЕРВОНИЙ, і кожен тест падає зі своєї причини
mvn -B test -Pstand -Dparallel=none -Dparallel.enabled=false -Dtest=FailureCausesTest
```

| Клас | Що показує | Що має статись |
|---|---|---|
| `DataConflictTest` | конфлікт тестових даних: два тести працюють з одним захардкодженим `test_user` | червоний при паралельному прогоні, зелений — при послідовному |
| `ParallelismTest` | гонка даних через спільне статичне поле `sharedUserSession` | червоний при паралельному прогоні (детерміновано, через `CountDownLatch`) |
| `ArtifactsTest` | збір діагностики при падінні: `.log`, `.png` і `.html` у `target/artifacts/` | червоний при паралельному прогоні, діагностика зібрана |
| `FailureCausesTest` | три причини падіння, які легко сплутати: елемент зʼявився пізно (`TimeoutException`), текст на сторінці змінився (`AssertionError` з різницею), бекенд віддав 500 (`AssertionError` із текстом помилки) | червоний завжди, у кожного тесту свій текст причини |

Червоний прогін тут не поломка, а результат: зелений означав би, що проблема не відтворилась.

`FailureCausesTest` піднімає власний стенд (`com.sun.net.httpserver.HttpServer` на випадковому порту),
тому не залежить від зовнішніх сайтів і мережі: падіння відтворюється однаково й локально, і в CI.
Кожен тест падає навмисно, тому зі звичайного прогону практик його виключено — інакше він би ламав
зелений результат для того, хто просто перевіряє свій фреймворк.

У CI ці вправи виконуються в окремій джобі **stand_practices**: послідовний прогін мусить бути зеленим,
паралельний — червоним, діагностику вивантажує крок «Завантаження діагностики з падіння» як артефакт
`diagnostic-artifacts` (його можна скачати зі сторінки прогону). Клас падінь запускається там окремим
кроком «Падіння з різних причин» — теж очікувано червоним, і джоба окремо перевіряє, що він справді
впав (зелений означав би, що вправі більше нема на чому вчити). Джоба перевіряє сам стенд, тому вона
не заважає прийманню capstone: за твої 5 тестів відповідає джоба `tests`.

## Вимоги до фреймворку

- Page Object: локатори — у константах класу, тести не знають про селектори.
- Жодних `Thread.sleep`: тільки `WebDriverWait`/`ExpectedConditions`.
- Тести незалежні один від одного (кожен сам логіниться).
- Fluent-методи Page Object-ів (повертають `this` або наступну сторінку).
